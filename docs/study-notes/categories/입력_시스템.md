# 입력 시스템 질문

Unity Input System의 액션 에셋, 생성 코드, 입력 수명주기에 관한 질문을 모은다.

## 생성된 입력 래퍼 초기화

- **`PlayerControls` 필드에 `[SerializeField]`를 붙였는데 IDE가 생성자 초기화를 추천하는 이유는 무엇인가?**  
  `[SerializeField]`는 직렬화 가능한 값을 Unity가 저장하고 복원하게 할 뿐, 객체를 생성하거나 C#의 미할당 필드를 초기화하지 않는다. `.inputactions`에서 생성된 `PlayerControls`는 `IInputActionCollection2`와 `IDisposable`을 구현한 일반 C# 래퍼이며 Unity 직렬화 타입이 아니므로 Inspector가 값을 넣어 줄 수도 없다. 따라서 Unity Analyzer는 `UAC1010`을 표시하고, IDE의 일반 C# 분석기는 별개로 미할당 필드를 보고 생성자 초기화를 제안한다. `MonoBehaviour`에는 그 생성자 추천을 적용하지 말고 `Awake`에서 `new PlayerControls()`로 생성한 뒤 `OnEnable`/`OnDisable`에서 활성 상태를 관리하고 `OnDestroy`에서 해제하는 방식이 적절하다. Inspector에서 입력 에셋을 참조하려는 설계라면 생성 래퍼 대신 `InputActionAsset` 또는 `InputActionReference`를 직렬화한다.

## 액션의 의미와 키 바인딩

- **Shift를 누르는 동안 걷게 하려면 기존 Interact 액션에 Shift를 추가해야 하는가?**  
  걷기 전환은 Interact와 의미가 다른 입력이므로 `WalkModifier` 또는 `Walk` 같은 별도의 Button 액션으로 만든다. 하나의 액션에 Space와 Shift를 함께 바인딩하면 두 키가 같은 행동을 발생시키는 대체 바인딩으로 취급되어 Shift도 Interact를 실행하게 된다. Shift의 누름과 해제 상태를 별도 액션으로 전달하고, 이동 시스템에서 그 상태에 따라 목표 이동 속도를 선택하는 편이 책임과 리바인딩 의미가 명확하다.

## 레거시 Input Manager 지원 경고

- **`This project uses Input Manager, which is marked for deprecation` 메시지가 나타나는 이유는 무엇인가?**  
  프로젝트의 주 입력 구조는 이미 Input System 패키지와 `PlayerControls`를 사용하지만, `SpecialWeekMiniController.Update()`에 애니메이션·표정 검증용 `Input.GetKeyDown` 호출이 남아 있다. 해당 컴포넌트가 붙은 `SpecialWeek_MINI_1001` 프리팹은 현재 이동 테스트 씬에서도 사용된다. 이 레거시 호출을 함께 지원하기 위해 Player Settings의 `Active Input Handling`이 `Both`(`activeInputHandler: 2`)로 되어 있으므로 Unity가 폐기 예정인 Input Manager도 활성화되어 있다고 안내하는 것이다. Cinemachine 자체의 오류는 아니다.

  당장은 `Both`를 유지하면 기존 검증 단축키와 새 Input System 입력이 모두 동작한다. 경고를 없애기 위해 바로 `Input System Package (New)`로 바꾸면 `SpecialWeekMiniController`의 레거시 입력 부분이 실행될 때 문제가 생길 수 있다. 최종적으로는 검증 단축키를 Input System 액션으로 옮기거나 런타임 캐릭터 프리팹에서 해당 검증용 컴포넌트를 분리한 뒤 `Input System Package (New)`만 사용한다.

## 클릭과 홀드 구분

- **일정 시간 이상 누르면 홀드가 시작되고, 그 전에 놓으면 클릭으로 처리하는 구조가 적절한가?**  
  일반적인 클릭/롱프레스 구분 방식이며 현재 `ClickGesture`에 적용하기 적절하다. 다만 누르는 즉시 홀드로 취급하는 현재의 `_pressed` 플래그만으로는 두 동작을 명확히 구분하기 어렵다. 입력 상태를 `Idle`, `Pending`, `Holding`으로 나누는 것이 핵심이다. 누르면 `Pending`에 들어가고, 임계시간 전에 놓으면 클릭 하나를 발행한 뒤 `Idle`로 돌아간다. 계속 누른 채 임계시간에 도달하면 홀드 `Start`를 한 번 발행하고 `Holding`으로 전이하며, 이후에만 `Hold`를 발행한다. `Holding`에서 놓았을 때만 홀드 `End`를 발행해야 홀드가 시작되지 않은 클릭 입력에 잘못된 `End`가 전달되지 않는다.

  시간 측정은 시스템 시계가 변경될 수 있는 `DateTime.Now`보다 Unity의 단조 증가 시간 계열을 일관되게 사용하는 편이 안전하다. 게임의 일시정지와 무관하게 UI 입력을 판정하려면 `Time.unscaledTimeAsDouble`이 적합하다. `InputAction.CallbackContext.time`과 포인터 이동 때 넣는 `Time.unscaledTimeAsDouble`처럼 서로 다른 출처를 한 계산에 섞지 말고, Gesture 내부에서 누름 시작과 현재 시간을 같은 기준으로 측정한다.

  클릭 좌표는 누른 위치와 놓은 위치 중 게임 규칙에 맞는 기준을 정해야 한다. 일반적인 선택은 놓은 위치를 사용하되, 누른 뒤 크게 이동한 입력까지 클릭으로 인정하지 않으려면 별도의 이동 허용 거리도 둔다. 현재 요구 범위에서는 시간만으로 먼저 분리할 수 있지만, 카메라 드래그가 추가되면 이동 거리 기반 취소 또는 Drag 상태가 필요하다.

  현재 소비자인 `InteractionUseCase`는 홀드 `Start`에서 실제 작업을 시작하고 `End`에서 중단한다. 따라서 임계시간을 도입하면 짧은 입력은 작업을 시작하지 않고 클릭 경로로만 전달되며, 긴 입력은 임계시간이 지난 시점부터 작업을 시작한다. 임계시간을 넘긴 입력은 놓을 때 클릭을 추가로 발생시키지 않아야 한다. 경계값은 `elapsed >= holdThreshold`를 홀드로 정의하고, 임계시간을 넘는 순간 `Start`와 매 프레임 `Hold`가 같은 프레임에 중복 발행될지 여부도 명시적으로 정하는 것이 좋다.

- **클릭과 홀드를 모두 지원하는 대상과 클릭만 지원하는 대상이 있고, 클릭 전용 대상은 오래 눌렀다 놓아도 클릭으로 처리해야 한다면 어떻게 하는가?**  
  누른 시간만으로 Gesture 계층에서 최종 행동을 확정하면 클릭 전용 대상의 요구를 처리할 수 없다. Gesture 계층은 `Pressed`, `HoldThresholdReached`, `Released`처럼 물리 입력에서 확인된 사실만 전달하고, 현재 누른 대상과 그 대상이 지원하는 상호작용을 아는 Interaction 계층이 Click/Hold 중 최종 행동을 선택하는 것이 적절하다.

  `Pressed` 시점에 Raycast로 대상을 한 번 선택하고 해당 대상을 입력 세션이 끝날 때까지 캡처한다. 대상이 Click과 Hold를 모두 지원하면 임계시간 전 Release는 Click, 임계시간 도달은 Hold Start, 이후 Release는 Hold End로 처리하며 Click은 발생시키지 않는다. Click만 지원하는 대상은 임계시간 도달 신호를 무시하고 얼마나 오래 눌렀든 Release에서 Click을 실행한다. 이렇게 하면 동일한 물리 입력이라도 대상의 능력에 따라 의미가 달라진다.

  지원 기능은 `PropType` 분기보다 `IClickInteractable`과 `IHoldInteractable` 같은 분리된 capability 인터페이스 또는 `[Flags]` 형태의 `SupportedInteractions`로 표현하는 편이 확장에 유리하다. 인터페이스 방식은 대상이 실제 행동까지 소유할 때 자연스럽고, 현재처럼 UseCase가 행동을 실행한다면 `IProp`이 지원 기능 정보만 제공하고 Interaction UseCase가 적절한 UseCase로 라우팅하는 방식이 더 잘 맞는다. `ClickOnly`, `ClickAndHold`처럼 조합마다 enum 값을 추가하면 HoldOnly나 Drag가 생길 때 조합 수가 늘어난다.

  현재 `ClickGesture`가 Click과 Hold를 독립 Observable로 최종 확정해 발행하는 구조를 그대로 유지하면 두 스트림 사이의 배타성을 각 소비자가 다시 관리해야 한다. 특히 모든 Release를 Click으로 발행하면 Click+Hold 대상에서 Hold End와 Click이 함께 실행될 수 있다. 따라서 공통 입력 단계 이벤트와 대상별 세션 상태(`Target`, `SupportsHold`, `HoldStarted`)를 Interaction 계층에 두는 편이 안전하다. 세션 대상은 Press 위치 기준으로 고정하고, 포인터가 허용 거리 이상 움직였을 때만 취소 또는 Drag로 전환하는 규칙을 별도로 둔다.

- **입력을 Press 시작, 임계시간 뒤 Hold 시작, Release로 판별하고 `IGestureReceiver`가 홀드 사용 여부·임계시간·Click/Hold 동작을 제공하는 구조는 어떤가?**  
  전체 흐름은 적절하다. Press 시점에 Receiver를 찾아 세션 대상으로 캡처하고, Receiver가 Hold를 지원할 때만 해당 임계시간 이후 Hold Start로 전이한다. Release 때 Hold가 실제 시작됐다면 Hold End만 호출하고, 시작되지 않았다면 누른 시간과 관계없이 Click을 호출하면 Click 전용 대상의 긴 입력도 요구대로 처리된다.

  다만 단일 `IGestureReceiver`에 `SupportsHold`와 모든 Hold 메서드를 넣으면 Click 전용 구현체가 사용하지 않는 Hold 메서드를 빈 구현으로 가져야 한다. 지원 기능 자체를 타입으로 표현할 수 있도록 `IClickGestureReceiver`와 `IHoldGestureReceiver`를 분리하고, Hold 지원 여부는 `IHoldGestureReceiver` 구현 여부로 판정하는 구성이 더 명확하다. Hold 임계시간은 `IHoldGestureReceiver.HoldThresholdSeconds` 같은 속성으로 둘 수 있다. Click과 Hold를 모두 지원하는 대상은 두 인터페이스를 함께 구현한다. 향후 Hold 전용이나 Drag가 추가되어도 조합 enum이나 bool을 늘리지 않고 capability를 조합할 수 있다.

  Receiver가 Unity 오브젝트에서 게임 상태를 직접 변경하게 만들지는 않는 편이 좋다. 현재 구조에서는 Receiver를 대상 식별과 입력 정책을 제공하는 어댑터로 사용하고 실제 Click/Hold 행동은 Interaction UseCase가 도메인 UseCase로 전달하거나, Receiver 콜백이 해당 UseCase 호출로 연결되도록 한다. Gesture 판별기는 Raycast나 `IProp`을 알지 않고 시간과 입력 단계만 관리해야 한다.

  세 단계 외에 `Cancel`도 수명주기에 포함하는 것이 안전하다. 누르는 동안 대상이 비활성화되거나 씬이 바뀌거나 포인터가 허용 거리 이상 이동하면 정상 Release와 구분해 세션과 진행 중 Hold를 정리해야 한다. `OnHold`가 매 프레임 꼭 필요한지는 소비자가 연속 위치나 진행 입력을 사용하는지에 따라 결정하고, 현재처럼 시작과 종료만 필요하다면 Hold Start/End만 전달해도 된다.
