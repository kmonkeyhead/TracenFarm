# 상호작용 시스템 질문

화면 선택, 상호작용 가능 거리, 대상 판정과 상호작용 수명주기에 관한 질문을 모은다.

## 캐릭터와 상호작용 대상의 거리 판정

- **`InteractionUseCase`에서 상호작용 대상에 사거리가 있을 때 현재 캐릭터와 거리는 어떻게 비교하는 것이 좋은가?**  
  현재 `InteractionUseCase`는 카메라 Raycast로 맞은 `GameObject`만 반환하고 곧바로 `IProp.StartInteract()`를 호출한다. 캐릭터 위치가 주입되어 있지 않고 `RaycastHit`의 충돌체 정보도 버리므로 거리 제한을 판정할 수 없는 구조다. `InteractionUseCase`에 캐릭터의 상호작용 기준점 `Transform`을 주입하고, Raycast 결과를 `GameObject`가 아니라 `RaycastHit`으로 유지한 뒤 상호작용 시작 직전에 거리를 검증하는 것이 적절하다.

  작은 대상이고 피벗이 대상 중심에 정확하다면 캐릭터 위치와 `prop.transform.position`을 비교해도 된다. 그러나 현재의 밭처럼 크거나 피벗이 한쪽에 치우친 대상은 중심점까지의 거리가 실제 가장자리까지의 거리와 크게 다르다. 이 경우 `hit.collider.ClosestPoint(characterPosition)`으로 대상 Collider에서 캐릭터와 가장 가까운 지점을 구한 뒤 비교한다. 단순 통과 여부만 필요하므로 `(closestPoint - characterPosition).sqrMagnitude <= range * range`를 사용하면 제곱근 없이 정확하게 판정할 수 있다. 지형 높이 차이를 거리에서 제외하는 게임 규칙이라면 비교 벡터의 `y`를 0으로 만든 뒤 제곱 길이를 계산한다.

  `RaycastHit.point`는 플레이어가 화면에서 실제로 누른 지점까지의 거리이므로 클릭한 지점 자체가 사거리 안이어야 한다는 규칙에 적합하다. 반면 `Collider.ClosestPoint`는 대상의 어느 부분이든 캐릭터에게 닿을 수 있으면 허용하는 규칙에 적합하다. 농장 오브젝트에는 후자가 일반적으로 더 자연스럽다. 카메라 Raycast의 `maxDistance`는 카메라와 대상 사이의 선택 거리일 뿐 캐릭터 상호작용 거리와 기준점이 다르므로, 캐릭터 사거리 검사를 대신할 수 없다.

  대상마다 사거리가 다르다면 `IProp`이 `InteractionRange`와 거리 기준을 제공하거나 `CanInteract(Vector3 actorPosition)`을 구현하게 하는 편이 좋다. `InteractionUseCase`는 대상 선택과 흐름을 조정하고, 개별 대상은 자신의 Collider·상호작용 지점·사거리 규칙을 캡슐화할 수 있다. 모든 대상이 동일한 사거리를 쓴다면 사거리를 캐릭터 설정에 두고 UseCase에서 공통 판정해도 된다.

  개념적인 공통 판정은 다음과 같다.

  ```csharp
  Vector3 actorPosition = _interactionOrigin.position;
  Vector3 closestPoint = hit.collider.ClosestPoint(actorPosition);
  Vector3 offset = closestPoint - actorPosition;
  offset.y = 0f; // 게임 규칙상 높이 차이를 무시할 때만 사용

  bool isInRange = offset.sqrMagnitude <= interactionRange * interactionRange;
  if (!isInRange)
  {
      return;
  }
  ```

  사거리 검사는 Hold 시작 시 한 번만 할지, Hold가 유지되는 동안 계속 검사할지도 정해야 한다. 상호작용 도중 캐릭터가 움직일 수 있다면 매 업데이트마다 범위를 재검사해 벗어났을 때 `StopInteract()`를 호출해야 하며, 상호작용 중 이동이 잠긴다면 시작 시 한 번의 검사로 충분하다.

- **큰 `FarmPlot`의 중심점 기준 거리 때문에 의도하지 않은 판정이 생길 때는 어떻게 하는가?**  
  2026-08-21 현재 구현처럼 `IProp.CanInteract(Vector3 actorPosition)`이 대상별 규칙을 담당하는 방향은 적절하다. 큰 밭은 중심이 아니라 밭의 실제 경계에서 Actor까지의 최단거리를 사용한다. 선택용 Raycast에 맞은 Collider를 그대로 사용하는 것보다 `FarmProp`에 상호작용 영역을 나타내는 전용 Collider를 직렬화해 두면, 당근이나 자식 Collider를 눌러도 항상 같은 밭 경계를 기준으로 판정할 수 있다.

  ```csharp
  [SerializeField] private Collider _interactionArea;
  [SerializeField] private float _interactionRange = 1.5f;

  public bool CanInteract(Vector3 actorPosition)
  {
      Vector3 closestPoint = _interactionArea.ClosestPoint(actorPosition);
      Vector3 offset = closestPoint - actorPosition;
      offset.y = 0f; // 밭 게임에서 높이를 사거리 규칙에서 제외할 경우

      return offset.sqrMagnitude <= _interactionRange * _interactionRange;
  }
  ```

  `Collider.ClosestPoint`는 회전과 실제 Collider 형상을 반영하지만 `collider.bounds.ClosestPoint`는 월드 축 기준으로 Collider를 둘러싼 박스만 사용하므로, 회전된 밭이나 불규칙한 형상에서는 실제보다 가까운 것으로 오판할 수 있다. 단순한 사각 밭이라도 별도의 BoxCollider를 밭의 사용 가능 영역에 맞추고 Actor 몸 중심의 높이까지 포함하도록 충분한 높이를 주는 것이 디버깅하기 쉽다. Trigger로 사용할지는 충돌 이벤트가 필요한지에 따른 선택이며, `ClosestPoint` 계산 자체를 위해 Trigger일 필요는 없다.

  Actor의 Rigidbody 중심과 밭 표면 높이 차이를 게임 거리로 취급하지 않는다면 위 코드처럼 마지막 비교에서 `y`를 제거한다. 높이 차이도 접근 제한에 포함해야 하는 절벽이나 층 구조라면 `y`를 제거하지 않는다. 아주 정확한 평면 발 위치가 필요하면 Actor에 별도의 `InteractionOrigin`을 두거나 Rigidbody 위치에서 발 높이 오프셋을 적용한다.

  현재 `InteractionUseCase`에는 거리 계산과 별도로 조건문 오류가 있다. `if (!targetObject.TryGetComponent<IProp>(out var prop))` 블록 안에서 `prop.CanInteract(...)`를 호출하므로 컴포넌트를 찾지 못한 경우 null인 `prop`을 사용하게 된다. 성공할 때 실행하도록 `!`를 제거하거나 실패 시 즉시 반환해야 한다. 밭의 선택 Collider가 자식에 있다면 `targetObject.GetComponentInParent<IProp>()`로 루트의 `FarmProp`을 찾는다. 또한 `_interact = true`는 Prop을 찾고 `CanInteract`가 성공해 `StartInteract()`를 호출한 뒤에 설정해야 실패한 시도가 진행 중 상호작용으로 남지 않는다.

## 밭 상호작용 프로그레스바의 책임

- **밭을 누르는 동안 프로그레스바를 올리는 동작을 밭 자체에서 처리해도 되는가?**  
  먼저 프로그레스가 나타내는 의미를 구분해야 한다. 밭 갈기, 물주기, 수확처럼 해당 밭의 실제 작업 완료율이라면 `FarmProp`이 진행 상태와 완료 조건을 소유하는 것이 맞다. 상호작용을 중단했다가 다시 시작할 때 진행도를 유지할지 초기화할지도 밭의 게임 규칙이다. 반면 모든 대상에서 공통으로 사용하는 “길게 누르기 1초가 지나면 상호작용 확정” 게이지라면 이것은 밭 상태가 아니라 입력·상호작용 세션 상태이므로 `InteractionUseCase` 또는 별도의 `InteractionSession`이 소유하는 편이 맞다.

  실제 진행 상태를 `FarmProp`이 소유하더라도 `UnityEngine.UI.Image`를 직접 변경하는 책임까지 한 클래스에 넣는 것은 규모가 커질수록 불리하다. 현재 `FarmProp`은 이미 당근 생성과 슬롯 관리, 사거리 판정을 담당하고 있으므로 UI까지 추가하면 게임 규칙을 테스트하기 어렵고 월드 공간 UI를 HUD로 교체할 때도 코드를 바꿔야 한다. 권장 구조는 `FarmProp`이 0~1의 진행 값과 시작·중단·완료를 관리하고, 별도의 `FarmProgressView`가 그 값을 받아 `Image.fillAmount`와 표시 여부만 갱신하는 것이다.

  ```csharp
  // 개념적 역할 분리
  public class FarmProp : MonoBehaviour, IProp
  {
      public float Progress01 { get; private set; }
      public event Action<float> ProgressChanged;

      // StartInteract/StopInteract와 시간 경과에 따라 Progress01 변경
  }

  public class FarmProgressView : MonoBehaviour
  {
      [SerializeField] private Image _fillImage;

      public void SetProgress(float progress01)
      {
          _fillImage.fillAmount = progress01;
      }
  }
  ```

  밭 프리팹 위에 붙는 월드 공간 게이지라면 `FarmProgressView`를 같은 프리팹의 자식으로 두고 `FarmProp`과 연결하면 된다. 화면에 하나만 존재하는 공용 HUD 게이지라면 HUD Presenter가 현재 상호작용 대상의 진행 이벤트를 구독하고, 대상이 바뀌거나 `StopInteract()`가 호출되면 구독을 해제한다. `InteractionUseCase`는 대상을 찾고 시작·중단을 전달하는 조정자 역할에 머물며 매 프레임 `Image`를 직접 다루지 않는다.

  프로토타입 단계에서 `FarmProp`이 직렬화된 `Image`의 `fillAmount`를 직접 올려도 기능상 문제는 없다. 다만 최소한 진행 수치 자체와 완료 판정은 UI 값에 저장하지 말아야 한다. `Image.fillAmount`는 표시 결과일 뿐 원본 상태가 아니므로 별도의 `float Progress01`을 원본으로 두고 View가 이를 표현하게 한다. Image 컴포넌트의 Type도 `Filled`로 설정해야 `fillAmount` 변화가 화면에 나타난다.

  현재 `StartInteract()`는 한 번만 호출되므로 시간이 흐르며 진행도를 올릴 주체도 정해야 한다. `FarmProp.Update()`에서 상호작용 중 플래그를 확인하는 방식, Coroutine, 또는 UseCase가 매 프레임 Tick을 전달하는 방식이 가능하다. 작은 현재 구조에서는 `StartInteract()`가 작업을 시작하고 `StopInteract()`가 중단하며 Farm 내부 Coroutine이 시간을 누적하는 방식이 단순하다. 중복 Start 방지, Stop 시 Coroutine 정리, GameObject 비활성화 시 정리, 완료 후 한 번만 보상하는 조건은 반드시 포함해야 한다.

## 당근 생산 요청, Repository 변경, 완료 이벤트

- **프로그레스 완료 후 이벤트를 보내고 `FarmService`가 Repository 수량을 올린 뒤 다시 이벤트를 보내야 하는가, 아니면 생성된 Farm들을 `FarmStore`에 저장해 처리해야 하는가?**  
  두 선택지는 같은 문제의 대안이 아니다. `FarmService`와 Repository는 생산 규칙 및 저장 상태를 담당하고, `FarmStore`는 필요하다면 현재 씬에 살아 있는 `FarmProp` 참조를 `FarmId`로 찾는 런타임 Registry 역할을 담당한다. 당근 수량을 안전하게 변경하기 위해 Farm GameObject 목록을 저장할 필요는 없다.

  “당근을 생산해 달라”는 아직 일어나지 않은 요청이므로 이벤트보다는 Command 또는 명시적인 메서드 호출이다. 처리자가 반드시 한 명이고 실패 여부를 호출자가 알아야 하기 때문이다. 반대로 Repository 갱신에 성공한 뒤의 “당근이 생산됐다”는 이미 일어난 사실이므로 Event이며 퀘스트, 효과음, 통계처럼 여러 독립 시스템이 구독할 수 있다.

  ```text
  FarmProp의 진행 완료
      → ProduceCarrot(FarmId) 명령
      → FarmService가 규칙 검사
      → Repository를 한 번 갱신
      → CarrotProduced(FarmId, Amount, NewTotal) 이벤트
      → Farm View / HUD / 퀘스트 / 사운드가 필요할 때 구독
  ```

  현재 규모에서는 메시지 버스를 거쳐 `ProduceCarrotRequested`를 발행하고 `FarmService`가 구독하는 것보다 `FarmProductionUseCase` 또는 `InteractionUseCase`가 `FarmService.ProduceCarrot(farmId)`를 직접 호출하는 편이 흐름과 실패 처리가 명확하다. 결과는 `bool`, enum 또는 Result 값으로 돌려받을 수 있다. 메시지 버스를 사용하더라도 요청은 `ProduceCarrotCommand`, 성공 알림은 과거형인 `CarrotProducedEvent`로 구분한다.

  현재 `FarmRepository`는 `ObservableList`의 변경 알림을 이미 제공한다. Farm 화면과 HUD가 단순히 최신 수량을 다시 그리는 목적이라면 Repository 변경을 구독하는 것만으로 충분하며, 같은 사실을 알리는 수동 이벤트를 다시 발행하면 중복 갱신과 순서 문제가 생길 수 있다. 별도 `CarrotProducedEvent`는 Repository 변경만으로 의미를 알 수 없는 퀘스트 진행, 업적, 사운드, 분석처럼 “생산 행위 자체”에 반응해야 하는 소비자가 실제로 생겼을 때 추가한다.

  수량이 무엇의 수량인지도 분리해야 한다. 밭에 현재 자라 있거나 수확 가능한 당근 개수라면 `FarmModel`에 저장할 수 있다. 플레이어가 소유한 전체 당근 아이템 개수라면 `FarmRepository`가 아니라 `InventoryRepository` 또는 `ItemRepository`가 원본이어야 한다. 한 번의 생산으로 밭 상태와 인벤토리가 동시에 바뀐다면 Service/UseCase가 두 변경을 하나의 작업으로 조정하고, 모두 성공한 뒤 완료 이벤트를 한 번 발행한다.

  `FarmStore` 또는 `FarmRegistry`가 필요한 경우는 여러 Farm이 동적으로 생성·제거되고, 외부 시스템이 `FarmId -> FarmProp`을 찾아 카메라 포커스나 월드 표시를 적용해야 할 때다. 그때도 Registry는 Unity 오브젝트 참조만 관리하고 저장 데이터의 원본은 Repository로 유지한다. 현재처럼 상호작용한 `FarmProp`이 이미 자기 자신과 `FarmId`를 알고 생산을 요청할 수 있다면, 당근 생산만을 위해 Registry를 추가할 필요는 없다.

  마지막으로 진행 완료 신호가 프레임이나 Coroutine 종료 과정에서 두 번 발생해도 생산이 중복되지 않게 해야 한다. Farm 상태를 `Ready -> Producing -> Produced`처럼 전이시키거나 생산 요청 ID를 사용하고, 최종 중복 방어는 `FarmService`에서 수행한다. 시각적 당근 활성화는 Repository가 성공적으로 갱신된 뒤에만 실행해야 데이터는 실패했는데 화면에 당근만 생기는 불일치를 피할 수 있다.

- **추후 특정 밭으로 바로 이동하는 기능이 필요하다면 `FarmStore`가 적절한가?**  
  이 경우에는 런타임 등록소가 적절하다. 이동 UseCase가 `FarmId`만 받고 현재 씬의 해당 Farm과 도착 지점을 찾아야 하므로 `FarmId -> IFarmLocation` 관계가 필요하다. 다만 저장 상태를 뜻하는 Store와 혼동하지 않도록 `FarmRegistry`라는 이름을 권장한다. `FarmRepository`는 작물 수량과 성장 상태처럼 저장할 데이터를, `FarmRegistry`는 현재 로드된 Unity 오브젝트의 참조를 담당한다.

  ```csharp
  public interface IFarmLocation
  {
      FarmId Id { get; }
      Vector3 ArrivalPosition { get; }
      Quaternion ArrivalRotation { get; }
  }

  public interface IFarmRegistry
  {
      bool TryGet(FarmId id, out IFarmLocation farm);
  }
  ```

  이동 위치로 `FarmProp.transform.position`이나 밭 Collider 중심을 그대로 사용하면 Actor가 밭 위, Collider 내부 또는 접근할 수 없는 위치에 놓일 수 있다. 각 Farm에 `_arrivalPoint` Transform을 두어 밭 입구나 통로의 안전한 위치와 바라볼 방향을 명시하고 Registry에는 `IFarmLocation`으로 노출한다.

  Farm이 생성되면 Spawn/Scene Registrar가 Registry에 등록하고, 제거되거나 씬이 언로드되면 해제한다. 바로 이동 UseCase는 Registry에서 목적지를 찾은 뒤 Actor 이동만 수행해야 하며, `FarmService`가 `FarmProp` 참조를 찾아 이동시키게 만들지는 않는다. 생산 규칙과 월드 이동은 서로 다른 책임이다.

  목적지 Farm이 다른 씬에 있어 아직 로드되지 않았다면 런타임 Registry만으로는 찾을 수 없다. 이 경우 영구적인 `FarmId -> SceneId/Address/논리 위치` 정보는 별도의 Farm Catalog 또는 저장 데이터에 두고, 먼저 씬을 로드한 뒤 새 씬의 Farm이 Registry에 등록되면 `_arrivalPoint`로 이동한다. 따라서 Registry는 현재 로드된 대상 검색에는 적합하지만 전체 월드 위치 데이터의 영구 저장소를 대신하지 않는다.

- **NPC가 밭을 찾아 상호작용해야 하므로 모든 밭의 상태와 위치가 필요하다면 어떻게 구성하는가?**  
  NPC가 “작업 가능한 가장 가까운 밭”을 선택하려면 전체 밭을 조회할 수 있는 구조가 필요하므로 `FarmRegistry`를 두는 방향이 맞다. 다만 상태와 위치의 원본을 한 객체에 중복 저장하지 않는다. 저장·불러오기 대상인 성장 단계, 작물 수량, 작업 가능 여부와 예약 상태는 `FarmRepository`의 `FarmModel`에 두고, 현재 씬의 실제 위치와 도착 지점은 `FarmRegistry`에 등록된 `FarmProp` 또는 `IFarmRuntime`에서 조회한다.

  ```text
  FarmRepository                         FarmRegistry
  FarmId → 저장되는 FarmModel           FarmId → 현재 로드된 IFarmRuntime
  (성장, 수량, 작업 상태, 예약)           (실제 위치, 도착점, 활성 여부)
                 \                     /
                  FarmQueryService
          “이 NPC가 작업할 수 있는 가까운 밭” 반환
  ```

  ```csharp
  public interface IFarmRuntime
  {
      FarmId Id { get; }
      Vector3 Position { get; }
      Vector3 ArrivalPosition { get; }
  }

  public readonly struct FarmCandidate
  {
      public FarmId Id { get; }
      public FarmState State { get; }
      public Vector3 ArrivalPosition { get; }
  }
  ```

  NPC의 Behavior 노드가 Repository와 Registry를 각각 직접 뒤지게 하지 말고 `FarmQueryService.FindNearestWorkable(actorPosition, workType)` 같은 질의 API를 사용한다. Query Service가 상태 조건으로 먼저 거르고 실제 위치로 거리를 비교해 `FarmCandidate`를 반환하면 AI는 선택과 이동에만 집중할 수 있다. 밭 수가 수십 개 정도라면 Registry를 순회해 제곱 거리를 비교하는 것으로 충분하고, 수백·수천 개가 되어 실제 측정상 병목이 생길 때 공간 해시나 구역 인덱스를 추가한다.

  여러 NPC가 동시에 같은 밭을 선택하는 경쟁 조건도 고려해야 한다. 단순 `IsAvailable` 조회 후 이동하면 두 NPC가 같은 밭을 선택할 수 있으므로 `FarmService.TryReserve(farmId, actorId)`처럼 조회 이후 원자적으로 예약한다. 성공한 NPC만 이동하며 작업 취소, Actor 제거, 경로 실패, 시간 초과 시 예약을 해제한다. 생산·성장 상태 전이와 예약의 최종 권한은 Farm GameObject가 아니라 `FarmService`에 두는 것이 좋다.

  고정된 밭의 위치를 매 프레임 Store에 복사할 필요는 없다. Registry가 `FarmProp.Position`을 조회할 때 Transform의 현재 값을 읽으면 된다. 다른 씬처럼 아직 로드되지 않은 밭까지 NPC 계획에 포함하려면 Farm Catalog에 씬/구역과 대략적인 논리 위치를 저장하고, 씬이 로드된 뒤 실제 Registry 위치로 전환한다.

- **Repository는 불변 모델만 보관하고 Store가 현재 상태까지 보관한다는 구분이라면 NPC 용도로 Store가 더 적합하지 않은가?**  
  그 정의를 프로젝트의 규칙으로 사용한다면 `FarmStore`가 더 적합하다. NPC, HUD, 상호작용 UseCase는 모두 “지금 이 순간 어느 밭이 어디에 있고 어떤 상태인가”를 묻기 때문에 현재 세션 상태를 집계하는 `FarmStore` 하나를 조회하면 된다. 앞서 말한 `FarmRegistry`의 역할을 이 Store 내부에 포함할 수도 있다.

  ```text
  FarmRepository
  └─ FarmModel 스냅샷 로드·저장

  FarmStore                 ← 현재 세션의 단일 원본
  ├─ 최신 FarmModel
  ├─ FarmProp/IFarmRuntime 참조
  ├─ 실제 위치와 도착점
  ├─ 현재 작업 상태
  └─ ReservedBy ActorId

  FarmService / NPC / HUD
  └─ FarmStore를 통해 현재 상태 조회·변경
  ```

  다만 `record` 같은 불변 모델이라는 사실은 값이 영원히 변하지 않는다는 의미가 아니다. 모델 인스턴스는 불변이어도 `model with { Value = value }`로 새 스냅샷을 만들고 기존 모델을 교체할 수 있다. 실제 현재 `FarmService.GrowFarm()`과 `GenericRepository.AddOrReplace()`가 바로 이 방식이므로, 현재 구현의 `FarmRepository`는 이름과 달리 최신 상태 컬렉션 및 변경 알림 Store 역할까지 이미 수행한다.

  따라서 지금 `FarmStore`를 추가해 양쪽에 `FarmModel.Value`, 성장 상태 등을 동시에 저장하면 어느 쪽이 최신인지 결정하기 어렵다. Store를 도입한다면 소유권을 다음처럼 명확히 바꾸는 것이 좋다.

  ```text
  게임 시작: Repository.LoadAll() → FarmStore 초기화
  씬 로드:   FarmProp → FarmStore.AttachRuntime(FarmId, runtime)
  상태 변경: FarmService → FarmStore에서 새 Model 스냅샷 생성
  저장 시점: FarmStore의 최신 Model → Repository.Save()
  씬 종료:   FarmStore.DetachRuntime(FarmId)
  ```

  이 구조에서 Repository는 DB나 파일과 연결되는 영속화 경계이고, 현재 상태 변경 알림과 NPC 질의는 Store가 제공한다. 그러면 NPC는 Repository와 Unity 오브젝트를 따로 조회하지 않고 `FarmStore.FindNearestAvailable(position, workType)`만 사용할 수 있다. Store가 너무 커지면 내부 구현을 상태 인덱스와 위치 Registry로 분리하더라도 외부에는 하나의 질의 API를 제공할 수 있다.

  Store에 모든 순간값을 무조건 넣을 필요는 없다. 여러 시스템이 판단에 사용하는 성장, 작업 가능 여부, 예약, 위치는 Store에 적합하지만 프로그레스바 보간값이나 일회성 애니메이션 시간처럼 해당 View만 사용하는 값은 `FarmProp`/View에 남겨도 된다. 상태를 Store로 승격하는 기준은 저장 필요성뿐 아니라 여러 시스템이 동일한 현재 값을 공유하고 질의해야 하는가이다.

- **FarmStore와 FarmPayload를 이용해 현재 밭 상태를 처리할 때 FarmPayload와 FarmProp은 어떻게 연동하는가?**  
  현재 구현에는 `FarmProp.Initialize(FarmPayload)`가 있지만 `FarmPayload`와 `FarmStore`가 비어 있다. 반면 `IFarmPayload`에는 `Position`, `WorkingCount`, `WorkingProgress`라는 읽기 전용 상태가 정의되어 있다. 이 상태에서 권장하는 관계는 **밭 하나당 FarmPayload 하나**, **FarmStore가 모든 FarmPayload를 FarmId로 소유**, **FarmProp은 자신과 같은 FarmId의 Payload를 주입받아 화면에 표현**하는 구조다.

  ```text
  FarmStore
  └─ Dictionary<FarmId, FarmPayload>       현재 세션 상태 소유
                    │
                    │ Initialize / Bind
                    ▼
               FarmProp                    Unity 월드 표현
               ├─ Transform, Collider
               ├─ 당근 GameObject
               └─ Payload 변경을 화면에 반영
  ```

  두 객체를 연결하려면 양쪽을 식별할 공통 `FarmId`가 먼저 필요하다. `FarmProp`에는 씬/프리팹에서 지정할 직렬화된 FarmId를 두고, `FarmStore`에는 `FarmId -> FarmPayload` 사전을 둔다. 씬 초기화 담당자(`InGameFlow`, 별도 `FarmRegistrar`, 또는 VContainer EntryPoint)가 모든 FarmProp을 등록하면서 Store에서 같은 Id의 Payload를 얻어 `prop.Initialize(payload)`를 호출한다. FarmProp의 `Awake()`에서 Store를 직접 검색하면 DI 초기화 순서와 테스트가 어려워지므로 조립은 외부 초기화 지점에서 하는 편이 안전하다.

  ```csharp
  // 개념 예시: 실제 구현 전 필드와 이벤트 형식은 확정해야 한다.
  public sealed class FarmStore
  {
      private readonly Dictionary<int, FarmPayload> _farms = new();

      public FarmPayload Get(int farmId) => _farms[farmId];

      public void Bind(FarmProp prop)
      {
          prop.Initialize(Get(prop.FarmId));
      }
  }
  ```

  `FarmProp.Initialize`의 매개변수는 가능하면 구체 클래스 `FarmPayload`보다 읽기 계약인 `IFarmPayload`로 받는다. 그러면 FarmProp은 상태를 읽고 표시하는 역할에 제한된다. 상태 변경은 FarmProp이 Payload의 필드를 직접 고치는 대신 `FarmService.GrowFarm(farmId)` 또는 `FarmService.CompleteWork(farmId, actorId)` 같은 명령을 호출하고, Service가 Store를 변경하도록 한다. Payload 변경 알림을 구독한 FarmProp은 `WorkingProgress`를 프로그레스바에, 생산 수량을 당근 활성 개수에 반영한다.

  ```text
  사용자/NPC 상호작용 완료
  → FarmService.CompleteWork(FarmId)
  → FarmStore의 FarmPayload 변경
  → Payload 변경 알림
  → FarmProp.Render(payload)
  ```

  `Position`은 소유권을 주의해야 한다. 현재 씬에 존재하는 밭의 정확한 위치는 `FarmProp.transform.position`이 원본이므로 고정 위치를 Payload에 매 프레임 복사하지 않는다. NPC가 Store만 통해 위치를 질의해야 한다면 Store가 FarmId와 `IFarmRuntime`/FarmProp 참조를 함께 등록하고 현재 Transform 값을 읽게 한다. 반대로 저장되지 않는 `Image.fillAmount` 보간값은 FarmProp/View에 둘 수 있다. 여러 Actor와 HUD가 공유해야 하는 실제 작업 진행률과 작업자 수만 Payload에 둔다.

  구현 순서는 (1) FarmId 추가, (2) FarmPayload에 Id와 공유 상태 및 변경 알림 추가, (3) FarmStore의 Id 사전과 등록 API 추가, (4) 초기화 담당자가 Prop과 Payload 연결, (5) FarmProp이 Payload 변경을 구독해 렌더링, (6) 완료 명령이 FarmService를 거쳐 Store를 바꾸도록 연결하는 순서가 적절하다. 비활성화/파괴 시에는 Payload 이벤트 구독과 런타임 참조 등록을 반드시 해제한다.

- **FarmStore에 FarmProp 자체를 보관하지 않아도 되는가?**  
  FarmStore의 책임을 논리 상태 저장과 조회로 한정한다면 FarmProp 자체는 없어도 된다. `Dictionary<FarmId, FarmPayload>`만으로 성장 상태, 작업 진행도, 생산 수량, 예약 여부를 처리할 수 있고, 각 FarmProp은 초기화 담당자로부터 자기 Payload를 한 번 주입받아 변경 알림만 구독하면 된다. 이 구조는 Store가 Unity의 MonoBehaviour에 의존하지 않아 테스트와 씬 전환이 단순하다는 장점이 있다.

  반면 NPC가 가장 가까운 밭을 찾거나 특정 밭으로 이동하고, 도착점·Collider·현재 Transform 같은 씬 정보를 Store를 통해 질의해야 한다면 Payload만으로는 부족하다. 이때도 Store에 구체 `FarmProp`을 노출하기보다 `IFarmRuntime`처럼 필요한 기능만 가진 인터페이스를 별도 등록한다.

  ```csharp
  public interface IFarmRuntime
  {
      int FarmId { get; }
      Vector3 Position { get; }
      Vector3 ArrivalPosition { get; }
  }
  ```

  Store 내부에는 논리 상태와 선택적인 런타임 참조를 분리해 둘 수 있다.

  ```text
  FarmStore
  ├─ Payloads[FarmId]  → 항상 유지되는 현재 논리 상태
  └─ Runtimes[FarmId] → 해당 씬이 로드된 동안만 등록
  ```

  따라서 현재 단계에서 생산량과 프로그레스 연동만 구현한다면 FarmProp을 Store에 넣지 않아도 된다. 이후 NPC 위치 탐색이 필요해지는 시점에 `AttachRuntime`/`DetachRuntime`을 추가하는 편이 불필요한 결합을 줄인다. Store가 FarmProp을 소유하는 것이 아니라 씬에 존재하는 동안 참조만 등록한다는 점도 중요하다. GameObject의 생성·파괴 수명은 씬 또는 Spawner가 담당한다.

- **특정 Farm에 상호작용해야 하는 AI는 FarmProp에 어떻게 접근하는가?**  
  Payload만 보관하는 Store에서는 AI가 논리 상태는 알 수 있지만 현재 씬의 위치, 도착점, 상호작용 범위는 알 수 없다. 따라서 물리적으로 밭에 접근해야 하는 AI 기능이 생기면 `FarmId -> IFarmRuntime` 등록 경로가 필요하다. AI가 `FindObjectsOfType<FarmProp>()`로 씬을 검색하거나 구체 FarmProp을 직접 의존하게 만들지 않고, Store 내부 Registry 또는 별도 FarmRegistry가 필요한 런타임 인터페이스만 제공한다.

  ```text
  FarmStore
  ├─ Payloads[FarmId]   → 작업 가능 여부, 진행도, 예약 상태
  └─ Runtimes[FarmId]  → 현재 위치, 도착점, 상호작용 거리 판정
  ```

  AI의 권장 흐름은 `후보 조회 → 예약 → 이동 → 도착 검증 → 작업 명령 → 완료/예약 해제`다. 먼저 `FarmQueryService.FindNearestWorkable()`가 Payload 조건과 Runtime 위치를 함께 사용해 후보를 고른다. AI는 `TryReserve(farmId, actorId)`에 성공한 뒤 `ArrivalPosition`으로 이동한다. 도착 후에는 FarmProp의 `StartInteract()`를 직접 부르기보다 `FarmInteractionService.TryStartWork(farmId, actorId)`를 호출하고, Service가 거리와 예약을 재검증한 뒤 Payload의 작업 상태를 바꾸게 한다. FarmProp은 Payload 변경을 구독해 프로그레스와 당근을 표현한다.

  ```text
  AI
  → FarmQueryService.FindNearestWorkable(actorPosition)
  → FarmService.TryReserve(farmId, actorId)
  → candidate.ArrivalPosition으로 이동
  → FarmInteractionService.TryStartWork(farmId, actorId)
  → FarmStore/FarmPayload 상태 변경
  → FarmProp 렌더링
  ```

  현재처럼 실제 진행 루프가 FarmProp의 `StartInteract()` 안에 있는 과도기에는 `IFarmRuntime`이 `CanInteract`, `StartInteract`, `StopInteract`를 임시로 노출하여 AI용 UseCase가 호출할 수 있다. 그러나 장기적으로 작업 진행과 보상 규칙은 Service/Store로 옮기고 Runtime은 위치·도착점·Collider 거리 판정만 제공하는 편이 플레이어와 AI가 같은 규칙을 공유하기 쉽다. AI에게 반환하는 후보도 FarmProp이 아니라 `FarmCandidate(FarmId, ArrivalPosition)` 같은 작은 DTO로 제한하면 Unity 오브젝트 결합을 피할 수 있다.

  런타임이 등록되지 않았다는 것은 해당 Farm이 현재 씬에 없다는 뜻으로 취급한다. 물리적 상호작용 후보에서는 제외하고, 다른 씬의 밭까지 계획해야 한다면 별도의 씬 로드·구역 이동 절차를 먼저 수행한다.

- **FarmPayload와 런타임 참조를 함께 보관하는 클래스 이름은 무엇이 적절한가?**  
  Store 내부에서 밭 하나를 나타내는 단순 항목이라면 `FarmEntry`가 가장 적절하다. `FarmContext`는 서비스나 실행 환경까지 포함하는 넓은 객체처럼 들리고, `FarmInstance`는 생성된 GameObject 자체로 오해할 가능성이 있다. `FarmEntry`는 FarmStore 사전의 한 항목이라는 의미가 분명하다.

  ```csharp
  public sealed class FarmEntry
  {
      public FarmPayload Payload { get; }
      public IFarmRuntime Runtime { get; private set; }

      public bool IsRuntimeAttached => Runtime != null;

      public FarmEntry(FarmPayload payload)
      {
          Payload = payload;
      }

      public void AttachRuntime(IFarmRuntime runtime) => Runtime = runtime;
      public void DetachRuntime() => Runtime = null;
  }
  ```

  `FarmProp`이 `IFarmRuntime`을 구현한다면 Entry에 `FarmProp`과 `IFarmRuntime`을 각각 저장하지 않는다. 두 필드는 실제로 같은 객체를 가리키므로 중복 참조가 된다. Store에는 `IFarmRuntime`으로만 보관하고, Unity 전용 기능이 반드시 필요한 코드는 Store 바깥의 View 계층에서 FarmProp을 직접 다룬다. 만약 질문의 의도가 정말로 두 종류의 서로 다른 런타임 객체를 묶는 것이라면 `FarmRuntimeBinding`도 가능하지만, 현재 Payload와 씬 Runtime을 한 단위로 묶는 용도에는 `FarmEntry`가 더 간결하다.

- **`public record FarmEntry(int Index, IFarmPayload Payload, IProp Prop);` 형태로 만들어도 되는가?**  
  모든 밭이 항상 씬에 존재하고 Entry를 단순한 불변 묶음으로만 사용한다면 문법과 기본 구조에는 문제가 없다. 그러나 `Index`가 리스트 순번이 아니라 밭의 영구 식별자라면 `FarmId`로 이름을 바꾸는 것이 안전하다. 리스트 정렬이나 생성 순서가 바뀌어도 FarmId는 유지되어야 하기 때문이다.

  AI 이동까지 고려하면 `IProp`에는 도착 위치가 없으므로 `IFarmRuntime : IProp`을 두고 이를 보관하는 편이 적합하다. 또한 씬 언로드 시 Runtime을 해제하고 재로드 시 새 FarmProp을 붙여야 한다면 positional record는 Runtime 하나를 바꾸기 위해 Entry 전체를 `with`로 교체해야 한다. Payload는 유지하고 Runtime만 Attach/Detach하는 수명 구조에는 `sealed class FarmEntry`가 더 자연스럽다.

  ```csharp
  public sealed class FarmEntry
  {
      public int FarmId { get; }
      public IFarmPayload Payload { get; }
      public IFarmRuntime Runtime { get; private set; }

      public FarmEntry(int farmId, IFarmPayload payload)
      {
          FarmId = farmId;
          Payload = payload;
      }

      public void AttachRuntime(IFarmRuntime runtime) => Runtime = runtime;
      public void DetachRuntime() => Runtime = null;
  }
  ```

  작은 프로토타입에서 모든 FarmProp의 수명이 고정이라면 `public sealed record FarmEntry(int FarmId, IFarmPayload Payload, IFarmRuntime Runtime);`도 충분하다. 다만 record의 값 동등성은 내부에 변경 가능한 Payload와 Unity 런타임 객체 참조를 넣었을 때 큰 이점이 없으므로, 현재 설계의 기본 선택은 class가 적합하다.

- **`ArrivalPosition`은 무엇을 하는 값인가?**  
  `ArrivalPosition`은 AI가 밭과 상호작용하기 위해 이동을 마칠 안전한 도착 위치다. `FarmProp.transform.position`은 보통 밭의 중심이므로 그곳으로 이동시키면 Actor가 흙 위나 Collider 내부에 들어가거나 NavMesh 밖에 도착할 수 있다. FarmProp 자식에 `ArrivalPoint` Transform을 두고 밭 가장자리나 통로처럼 접근 가능한 좌표를 지정한 뒤 Runtime이 그 위치를 노출한다.

  ```csharp
  [SerializeField] private Transform _arrivalPoint;
  public Vector3 ArrivalPosition => _arrivalPoint.position;
  ```

  AI는 이 좌표까지 이동한 뒤 `CanInteract(actor.Position)`으로 실제 상호작용 범위에 들어왔는지 다시 확인한다. 작은 밭과 AI 하나에는 단일 ArrivalPosition으로 충분하다. 큰 밭이나 여러 AI가 동시에 작업한다면 한 지점에 몰릴 수 있으므로 여러 작업 지점을 두거나 `GetArrivalPosition(Vector3 actorPosition)`으로 Actor에게 가장 가까운 빈 작업 지점을 선택하는 형태가 더 적합하다. 이동 시스템이 Collider 경계와 NavMesh의 유효 위치를 직접 계산할 수 있다면 고정 ArrivalPosition은 필수 값이 아니다.

- **`ArrivalPosition`을 IProp에 넣어도 되는가?**  
  모든 IProp이 Actor가 이동해서 접근해야 하는 대상이라는 프로젝트 규칙이라면 넣어도 된다. 현재 대상이 FarmProp뿐인 프로토타입에서는 `IProp.ArrivalPosition`이 가장 단순한 선택이다. 그러면 AI는 구체 FarmProp이나 별도 Runtime 타입을 몰라도 IProp만으로 이동과 상호작용을 처리할 수 있다.

  그러나 IProp의 본래 공통 책임이 `CanInteract`, `StartInteract`, `StopInteract`이고 향후 문, 버튼, 즉시 클릭 대상처럼 고정 도착점이 필요 없는 Prop이 추가된다면 모든 구현체에 불필요한 ArrivalPosition을 강제하게 된다. 이 경우 인터페이스 분리 원칙에 따라 `IApproachable` 또는 `IInteractionLocation`을 별도로 두는 편이 적절하다.

  ```csharp
  public interface IApproachable
  {
      Vector3 GetApproachPosition(Vector3 actorPosition);
  }

  public class FarmProp : MonoBehaviour, IProp, IApproachable
  {
      // 상호작용과 접근 위치를 각각 구현한다.
  }
  ```

  고정 프로퍼티보다 `GetApproachPosition(actorPosition)` 함수가 큰 밭의 여러 가장자리나 여러 작업 지점 중 Actor에게 적합한 곳을 선택하기 쉽다. 결론적으로 현재 빠른 구현에는 IProp에 넣어도 되지만, 여러 종류의 Prop을 고려한 기본 설계에는 별도 접근 인터페이스가 더 유연하다.

- **현재 FarmProp과 FarmPayload를 분리한 구현은 올바른가?**  
  `FarmEntry(IFarmPayload Payload, IProp Prop)`와 `FarmStore.Register()`를 통해 논리 객체와 씬 객체를 FarmId로 연결하는 골격은 만들어졌다. `InGameFlow.CreateMap()`이 Payload를 생성하고 Store가 Prop의 Id를 초기화하는 조립 방향도 적절하다. `dotnet build Assembly-CSharp.csproj --no-restore`는 오류 0개로 통과했다. Unity 6000.5.7f1 배치 검증은 프로젝트 경로 설정 직후 반환 코드 1로 종료되어 Unity Editor 기준 검증은 완료되지 않았다. 다만 현재 상태 책임은 아직 완전히 분리되지 않았고 다음 실행 오류와 중복 상태가 있다.

  1. `FarmPayload` 생성자에서 `Id = Id;`로 대입하여 매개변수 `id`가 저장되지 않는다. 현재 생성한 `FarmPayload(1, ...)`도 실제 Id는 기본값 0이다. 여러 Farm을 등록하면 모두 키 0이 되어 `Dictionary.Add()`에서 중복 키 예외가 발생한다. `Id = id;`가 되어야 한다.
  2. `WorkingProgress`는 Payload에 생성 시 값만 들어가고 이후 변경할 방법이 없다. 실제 진행률은 `FarmProp.FillProgressAsync()`의 지역 변수 `progress`가 관리한다. 따라서 진행률의 단일 원본은 아직 Payload가 아니라 Prop이며, AI/HUD/저장에서 현재 진행률을 조회할 수 없다.
  3. `WorkingCount`는 Payload에 있지만 FarmProp에도 `_workerCount`로 복사된다. 시작할 때만 `SetWorkerCount()`가 호출되고 중단하여 Payload Count를 감소시킬 때는 Prop 값을 갱신하지 않으므로 두 값이 달라진다. Payload를 단일 원본으로 삼고 Prop이 변경 알림을 구독하거나, 진행 로직 자체를 Service/Store로 옮겨야 한다.
  4. `CheckAndInteract()`는 조건 검사 전에 `prop.StartInteract()`를 호출하고, 허용 조건 안에서 다시 `entry.Prop.StartInteract()`를 호출한다. 한 입력에 두 번 시작되어 첫 CancellationTokenSource가 즉시 취소·교체된다. 시작 호출은 작업자 수 증가에 성공한 뒤 한 번만 실행해야 한다.
  5. 최대 작업자 수가 1일 때 `entry.WorkingCount <= availableCount`는 Count가 이미 1이어도 통과하여 2가 된다. 추가 전 검사라면 `< availableCount`가 되어야 한다. 허용되지 않은 경우에는 `_lastProp`도 설정하거나 작업을 시작하면 안 된다.
  6. `FarmStore.Get()`과 `Register()`는 존재하지 않는 ID와 중복 ID에서 바로 예외를 발생시킨다. 프로토타입에서는 가능하지만 AI와 동적 씬 등록까지 고려하면 `TryGet`, `TryAdd` 또는 명시적인 Replace/Attach 정책이 필요하다.

  현재 평가는 “Payload와 Prop을 별도 타입으로 나누고 Store에서 연결하는 구조 분리는 성공했지만, WorkingCount와 WorkingProgress의 상태 소유권 분리는 미완성”이다. 우선 ID 대입 오류와 이중 Start/작업자 제한 조건을 고친 뒤, 진행률을 Payload/Store가 소유하고 FarmProp은 표시만 하도록 옮기는 순서가 적절하다.

- **FarmProgress를 Payload로 처리한다면 시간에 따른 Progress 업데이트는 어디서 해야 하는가? UseCase에서 async로 처리해도 되는가?**  
  Payload는 `WorkingProgress` 값을 보관하고 유효 범위를 지키는 상태 객체로 두되, 매 프레임 시간을 흘려보내는 실행 루프까지 소유하게 만들지는 않는다. InteractionUseCase도 사용자의 입력을 작업 시작·중단 명령으로 바꾸는 조정자이므로 장시간 async 루프를 직접 관리하면 입력 책임, CancellationToken 수명, 다중 Actor 처리와 진행 규칙이 한 클래스에 섞인다. 프로토타입에서는 가능하지만 AI까지 고려한 기본 구조로는 별도의 `FarmProgressSystem` 또는 `FarmWorkService`가 적합하다.

  ```text
  Player InteractionUseCase ─┐
                             ├→ FarmWorkService.Join/Leave
  AI 행동 ───────────────────┘
                                      │
                                      ▼
                         FarmProgressSystem.Tick(deltaTime)
                                      │
                                      ▼
                         FarmPayload.WorkingProgress 변경
                                      │
                                      ▼
                              FarmProp/View 렌더링
  ```

  다중 Actor에서는 Actor마다 async 루프를 만들지 않고 밭마다 진행 상태 하나만 갱신해야 한다. Player와 AI가 작업에 참여하면 Payload의 WorkingCount 또는 작업자 ID 집합을 변경하고, ProgressSystem은 활성 밭을 한 번씩 순회하면서 `deltaTime * 작업 속도 * WorkingCount`만큼 진행시킨다. 작업자 한 명이 나가도 다른 작업자가 남아 있다면 진행 루프는 계속되어야 하므로 현재 FarmProp처럼 한 Actor의 Stop이 공용 CancellationToken을 취소하는 구조는 맞지 않는다.

  VContainer를 사용 중이므로 `FarmProgressSystem : ITickable` 같은 EntryPoint로 매 프레임 Store의 활성 Entry를 갱신하는 방식이 가장 단순하고 테스트하기 쉽다. Payload에는 `AdvanceProgress(delta)`나 내부 setter를 제공하고, 완료 시 ProgressSystem/FarmWorkService가 작물 증가·진행도 초기화 같은 상태 전이를 한 번만 수행한다. UseCase는 `TryJoinFarm(farmId, actorId)`와 `LeaveFarm(farmId, actorId)`만 호출한다.

  UniTask를 선호한다면 async 자체가 문제는 아니지만 위치는 UseCase가 아니라 FarmWorkService가 적합하다. `Dictionary<FarmId, CancellationTokenSource>`로 밭마다 최대 하나의 루프를 보장하고, 씬/서비스 Dispose 토큰과 연결하며, WorkingCount가 0일 때 일시정지 또는 종료하는 게임 규칙을 명시한다. 현재 규모와 여러 Farm을 함께 갱신하는 요구에는 여러 async 루프보다 중앙 Tick 방식이 더 명료하다.

- **UniTask async에서 다음 Update까지 기다리는 API는 무엇인가?**  
  정확히 다음 프레임의 Update에서 재개하려면 `await UniTask.NextFrame(cancellationToken);`을 사용한다. 현재 프로젝트에 설치된 UniTask 구현도 NextFrame을 “다음 프레임 실행을 보장하는 Yield 유사 API”로 정의하며 기본 PlayerLoopTiming은 Update다.

  `await UniTask.Yield(PlayerLoopTiming.Update, cancellationToken);`은 실행을 Update 타이밍으로 양보하지만 호출 위치에 따라 다음 프레임을 반드시 보장하는 의미는 아니다. 한 프레임에 진행 계산을 정확히 한 번 수행하려는 루프에는 NextFrame이 의도가 더 분명하다. FixedUpdate를 기다리려면 `UniTask.Yield(PlayerLoopTiming.FixedUpdate, token)` 또는 프로젝트 API가 제공하는 `WaitForFixedUpdate(token)`을 사용하고, 프레임 마지막은 `WaitForEndOfFrame(token)`을 사용한다.

- **FarmPayload를 PropPayload로 변경하는 것이 적절한가?**  
  현재 FarmPayload의 `Id`, `WorkingCount`, `WorkingProgress`는 작물 종류, 성장 단계, 생산량처럼 Farm에만 해당하는 값이 아니라 작업 가능한 소품의 공통 상호작용 상태다. 따라서 Farm 전용이라는 잘못된 범위를 제거한다는 점에서 일반화 방향은 타당하다.

  다만 Payload는 일반적으로 전달용 DTO나 일회성 메시지라는 인상을 주고, 현재 객체는 Store 안에서 계속 변경되는 현재 상태이므로 `PropState` 또는 범위를 더 좁힌 `PropInteractionState`가 의미상 더 정확하다. 프로젝트에서 Payload를 런타임 상태라는 용어로 일관되게 사용하기로 했다면 `PropPayload`도 가능하다.

  이름을 일반화할 때 Payload만 바꾸고 `FarmEntry`, `FarmStore`가 그대로면 책임의 범위가 어긋날 수 있다. 모든 Prop을 하나의 Store에서 관리하려는 설계라면 `IPropState/PropState`, `PropEntry`, `PropStore`까지 함께 일반화하고, Farm 고유 상태는 별도의 `FarmState` 또는 `FarmData`로 분리한다.

  ```text
  PropState
  ├─ PropId
  ├─ WorkingCount 또는 WorkerIds
  └─ WorkingProgress

  FarmState
  ├─ CropType
  ├─ CropCount
  └─ GrowthStage
  ```

  반대로 실제로 Store가 Farm만 조회하고 Farm 작업 규칙만 처리할 계획이라면 현재 이름을 유지하는 편이 낫다. 아직 존재하지 않는 여러 Prop을 예상해 너무 일찍 일반화하면 문, 상자, 버튼처럼 진행률이나 작업자 수가 없는 대상에도 불필요한 필드를 강제할 수 있다. 이때는 `IPropState`에 모든 필드를 넣기보다 `IWorkablePropState`처럼 작업 가능한 Prop 전용 계약을 두는 것이 적절하다.

  여러 PropType이 각자 1번 Id를 가질 수 있다면 Store 키도 단순 int가 아니라 `PropKey(PropType, Id)` 또는 전역 고유 PropId로 정해야 한다. 결론적으로 현재 세 필드만 본다면 FarmPayload보다 Prop 공통 상태 이름이 맞고, 추천 이름은 `PropInteractionState`, 짧은 이름을 원하면 `PropState`, 기존 명명 규칙을 유지하려면 `PropPayload` 순이다.

- **ReactiveProperty로 Progress 표시를 연결한 뒤 Progress가 1이 되었을 때 당근 상태와 FarmProp은 어떻게 갱신하는가?**  
  현재 FarmProp은 `Awake()`에서 슬롯 수만큼 당근을 미리 Instantiate하고 모두 비활성화한다. 따라서 작업 완료 때 당근을 새로 생성하는 것이 아니라 원본 FarmModel의 당근 개수를 증가시키고, 변경된 개수를 FarmProp이 받아 기존 당근 풀의 앞쪽 N개를 활성화하는 방식이 현재 구조와 맞다.

  권장 흐름은 다음과 같다.

  ```text
  PropsProgressService: Progress가 1을 넘는 순간 감지
  → PropWorkCompleted(PropType.Farm, PropId)
  → Farm 완료 Handler/UseCase
  → FarmService.GrowFarm(FarmId)
  → FarmRepository의 새 FarmModel(Value + 1)
  → Farm 상태 Projection 또는 Presenter
  → FarmProp.RenderCarrotCount(newValue)
  ```

  완료 메시지를 모든 종류의 Prop UseCase가 구독한 뒤 자신에게 해당하는지 각각 검사하게 만들면 새 Prop 종류가 생길수록 불필요한 구독과 분기 및 해제 관리가 증가한다. 현재 Farm만 있다면 ProgressService가 하나의 `IPropWorkCompletionHandler`를 호출해도 충분하다. 여러 종류가 생기면 `PropType -> IPropCompletionHandler` 사전을 가진 Router가 정확히 한 Handler로 전달하는 구조가 적합하다. 메시지 버스는 업적, 사운드, 튜토리얼처럼 동일한 완료 사실을 여러 독립 시스템이 관찰해야 할 때 추가한다.

  FarmModel을 변경한 뒤 View를 갱신하는 방법은 두 가지가 있다. 현재 ReactiveProperty 방향을 유지하려면 Farm 전용 런타임 상태에 `ReactiveProperty<int> CarrotCount`를 두고 Repository 변경을 동기화한 다음 FarmProp이 이를 구독한다. 여기서 FarmModel이 원본이고 ReactiveProperty는 화면용 Projection이다. 더 단순하게는 FarmPresenter가 Repository 변경 이벤트를 구독하여 같은 Id의 FarmProp에 `RenderCarrotCount(model.Value)`를 호출해도 된다. FarmProp이 Repository를 직접 조회하거나 완료 메시지를 직접 해석하게 만들지는 않는다.

  ```csharp
  private void RenderCarrotCount(int count)
  {
      int visibleCount = Mathf.Clamp(count, 0, _carrots.Count);
      for (int i = 0; i < _carrots.Count; i++)
      {
          _carrots[i].SetActive(i < visibleCount);
      }
  }
  ```

  이 렌더 함수는 작업 완료뿐 아니라 저장 데이터 로드, 씬 재진입, 디버그 값 변경에도 같은 결과를 만든다. `_testIndex++`처럼 View 내부의 별도 카운터를 원본으로 사용하면 Model과 화면이 어긋나므로 제거하는 방향이 맞다.

  Progress 완료 판정도 `Clamp01` 후 다음 프레임에 0으로 만드는 것보다 증가 직후 경계를 넘었는지 검사하여 완료를 정확히 한 번 발생시키는 것이 안전하다. 한 프레임에 1을 초과한 나머지를 보존하려면 `progress -= 1f`를 사용하고, 최대 작물 수에 도달하면 더 이상 완료를 발생시키지 않는 규칙을 둔다. 현재 FarmProp에 남아 있는 기존 `FillProgressAsync()`와 `_testIndex` 당근 활성화 코드는 새 PropsProgressService 흐름과 중복이므로 최종적으로는 제거되어야 한다.

- **FarmModel은 현재 완성된 당근 수를 알아야 한다.**  
  맞다. 완성되어 밭에 존재하거나 수확 가능한 당근 수는 저장·불러오기, 오프라인 상태, 씬 재진입에도 유지되어야 하는 게임 상태이므로 FarmModel이 단일 원본이어야 한다. 현재 `FarmModel.Value`가 그 의미라면 `ReadyCarrotCount`, `GrownCarrotCount` 또는 프로젝트 용어에 맞는 `CarrotCount`로 이름을 구체화하는 것이 좋다.

  ```csharp
  public record FarmModel(int Id, int ReadyCarrotCount) : IModel;
  ```

  Progress 완료 시 FarmService가 기존 Model을 `with`로 교체하고 Repository에 저장한다. 값은 0부터 밭 슬롯 용량 사이로 제한한다. 수확 시에도 같은 Model 값을 감소시킨다.

  ```text
  작업 완료 → ReadyCarrotCount + 1
  당근 수확 → ReadyCarrotCount - 1
  씬 로드   → ReadyCarrotCount만큼 FarmProp 당근 활성화
  ```

  ReactiveProperty의 CarrotCount를 추가하더라도 원본 상태로 사용하지 않는다. Repository의 FarmModel 변경을 Presenter/Synchronizer가 받아 ReactiveProperty에 한 방향으로 복사하고, FarmProp은 그 값을 구독해 렌더링한다. 즉 `FarmModel → Reactive Projection → FarmProp`만 허용하며 FarmProp 또는 Projection이 Model과 독립적으로 개수를 증가시키지 않는다. 더 단순하게는 Presenter가 Model 변경 시 FarmProp의 `RenderCarrotCount(model.ReadyCarrotCount)`를 직접 호출해 중간 CarrotCount ReactiveProperty를 생략해도 된다.

  WorkingProgress는 작업 중인 세션 상태이므로 중단 시 초기화되고 저장할 필요가 없다면 PropState에 남긴다. 반대로 게임 종료 후에도 부분 진행률을 보존해야 한다면 그것도 FarmModel의 저장 필드로 승격한다. 완성 당근 수와 진행 중 Progress는 수명과 저장 요구가 다르므로 분리한다.

- **PropsProgressService에서 FarmService를 직접 참조해도 되는가?**  
  VContainer 수명 방향만 보면 가능하다. 현재 PropsProgressService는 InGame 자식 Scope에 있고 FarmService는 Root 부모 Scope에 있으므로 자식 객체가 부모 객체를 주입받는 것은 유효하다. 반대인 Root FarmService가 InGame PropsProgressService에 의존하는 것은 불가능하다.

  설계 판단은 ProgressService의 범위에 달려 있다. 이 클래스가 Farm 진행만 처리하고 앞으로도 Farm 완료만 발생시킨다면 이름을 `FarmProgressService`로 좁히고 FarmService를 직접 호출하는 것이 단순하고 적절하다. 반면 현재 이름처럼 여러 Prop 종류의 공통 진행을 처리한다면 FarmService 직접 의존은 공통 계층에 Farm 규칙을 끌어들이므로 피하는 편이 좋다.

  공통 ProgressService는 `PropType + PropId` 완료 결과만 만들고 `IPropCompletionRouter` 또는 `IPropWorkCompletionHandler`를 호출한다. Farm Handler가 FarmService에 의존하여 `GrowFarm(farmId)`를 수행한다.

  ```text
  PropsProgressService
  → IPropCompletionRouter.Complete(PropType, PropId)
  → FarmCompletionHandler
  → FarmService.GrowFarm(FarmId)
  ```

  메시지 버스는 필수가 아니다. 완료를 처리할 대상이 정확히 하나라면 인터페이스를 통한 직접 호출이 흐름 추적과 테스트가 더 쉽다. 업적, 사운드, 퀘스트처럼 여러 독립 시스템이 같은 완료 사실을 관찰해야 할 때 완료 처리 후 도메인 이벤트를 추가한다. 현재 단계의 추천은 PropsProgressService에는 Router/Handler 인터페이스를 주입하고 FarmService는 Farm 전용 Handler에서 참조하는 구조다. 프로토타입이고 Farm만 존재한다면 직접 참조로 시작해도 기능상 문제는 없다.

- **Prop 작업 완료 전달에 VitalRouter를 사용한다.**  
  현재 프로젝트에는 VitalRouter 2.8.0과 VContainer 연동 패키지가 설치되어 있다. PropsProgressService는 `ICommandPublisher`만 의존하여 완료 사실을 발행하고, `[Routes]` Farm Handler가 해당 명령을 받아 FarmService를 호출하는 구조로 연결한다. Handler는 FarmProp을 직접 갱신하지 않으며 FarmService의 Model 변경 이후 기존 Repository/Reactive Projection 경로가 화면을 갱신한다.

  ```csharp
  public readonly struct PropWorkCompletedCommand : ICommand
  {
      public PropType PropType { get; }
      public int PropId { get; }

      public PropWorkCompletedCommand(PropType propType, int propId)
      {
          PropType = propType;
          PropId = propId;
      }
  }
  ```

  PropsProgressService는 Progress가 경계를 넘은 순간 값을 먼저 1 미만으로 되돌린 뒤 완료 명령을 `await publisher.PublishAsync(command)`로 발행한다. 먼저 상태를 갱신해야 Handler 실행 중 재진입하거나 다음 프레임이 시작되어도 같은 완료를 중복 발행하지 않는다. Fire-and-forget보다 await가 완료 처리 순서와 예외 전파를 명확하게 한다.

  ```csharp
  [Routes]
  public partial class FarmWorkCompletedHandler
  {
      private readonly FarmService _farmService;

      public FarmWorkCompletedHandler(FarmService farmService)
      {
          _farmService = farmService;
      }

      [Route]
      public void On(PropWorkCompletedCommand command)
      {
          if (command.PropType != PropType.Farm) return;
          _farmService.GrowFarm(command.PropId);
      }
  }
  ```

  InGameContent의 VContainer 설정에서 `RegisterVitalRouter`와 `routing.Map<FarmWorkCompletedHandler>()`로 Handler를 등록한다. InGame 자식 Scope의 Handler가 Root Scope의 FarmService를 주입받는 방향은 유효하다. 명령 타입과 Handler 클래스는 VitalRouter 소스 생성 조건에 맞게 각각 `ICommand`, `[Routes] partial`, `[Route]`를 사용한다.

  ```text
  PropsProgressService
  → VitalRouter: PropWorkCompletedCommand
  → FarmWorkCompletedHandler
  → FarmService.GrowFarm
  → FarmModel.ReadyCarrotCount 변경
  → Reactive Projection
  → FarmProp 당근 표시
  ```

  현재처럼 완료 명령 하나를 여러 Prop Handler가 받는 구조는 작은 종류 수에서는 충분하다. 종류가 많아져 모든 Handler의 `PropType` 필터가 반복되면 VitalRouter의 첫 Handler에서 타입별 명령으로 변환하거나 Prop 타입별 완료 Command를 발행하는 라우팅 계층을 추가한다. 당근 생성, UI, 사운드를 모두 Farm Handler에 넣지 말고 Farm Handler는 Model 변경만 담당하며, 다른 독립 반응은 Model 변경 또는 별도의 Farm 성장 완료 명령을 관찰하게 한다.

  첫 구현 튜토리얼에서는 별도 Farm Handler를 만들지 않고 FarmService 자체를 VitalRouter Handler로 매핑한다. FarmService와 Router를 RootLifeTimeScope에 등록하면 InGame 자식 Scope의 PropsProgressService가 부모의 `ICommandPublisher`를 주입받아 발행할 수 있다.

  1. `PropWorkCompletedCommand`를 `readonly struct : ICommand`로 정의한다. Unity 객체나 Prop 참조를 넣지 않고 PropType과 PropId만 전달한다. VitalRouter 문서는 record struct를 권장하지만 현재 Assembly-CSharp의 LangVersion이 9.0이므로 C# 10의 record struct는 사용할 수 없다.
  2. PropsProgressService 생성자에 `ICommandPublisher`를 주입한다. Progress가 1을 넘으면 먼저 나머지 Progress를 저장한 뒤 `await PublishAsync()`를 호출한다.
  3. FarmService를 `[Routes] partial` 클래스로 바꾸고 `[Route] On(PropWorkCompletedCommand)`에서 Farm 타입만 받아 `GrowFarm(command.PropId)`를 호출한다.
  4. RootLifeTimeScope에서 기존 FarmService 등록 이후 `RegisterVitalRouter(routing => routing.Map<FarmService>())`를 호출한다. InGameContent에는 별도의 Router를 다시 등록하지 않는다.
  5. GrowFarm이 FarmModel의 완성 당근 수를 변경하는지 확인하고 Repository 변경 경로를 통해 FarmProp을 렌더링한다.

  ```text
  RootLifeTimeScope
  ├─ FarmService + VitalRouter Route
  └─ Router/ICommandPublisher

  InGameContent (자식)
  └─ PropsProgressService → 부모 ICommandPublisher 사용
  ```

  Progress 완료 명령은 작업 완료 요청이므로 FarmService가 원본 Model을 실제로 바꾼다. FarmProp은 이 Command를 구독하지 않고 Model 변경 결과만 표현한다. 나중에 Prop 종류가 늘어 FarmService의 타입 필터가 반복되기 시작하면 그 시점에 Router 전용 Handler 또는 타입별 Command로 분리한다.

## DI로 캐릭터 위치를 가져오는 방법

- **`InteractionUseCase`에 DI로 `PlayerController`를 주입해야 하는가, 아니면 캐릭터 위치를 실시간 저장하는 별도 장소에서 가져와야 하는가?**  
  현재 프로젝트에서 `PlayerController`는 입력을 받아 `_actor`에 명령을 전달하는 컴포넌트이고, 실제 이동과 Rigidbody는 별도의 `Actor` GameObject에 있다. 씬에서도 `PlayerController`와 `Actor`의 Transform이 서로 다르므로 `PlayerController.transform.position`은 실제 캐릭터 위치가 아니다. `InteractionUseCase`가 필요한 것은 입력 제어 기능이 아니라 상호작용 기준 위치 하나이므로 `PlayerController` 전체에 의존하는 것도 책임이 과하다.

  캐릭터 위치를 매 프레임 다른 서비스에 복사해 저장하는 방식도 권장하지 않는다. Rigidbody/Transform이라는 원본과 위치 저장소라는 사본이 생겨 업데이트 순서, 물리 틱, 씬 전환에 따라 값이 어긋날 수 있다. 대신 실제 위치의 소유자인 `Actor`를 DI로 연결하되, UseCase에는 `Actor` 전체보다 `IInteractionActor` 또는 `IInteractionOrigin` 같은 좁은 읽기 인터페이스를 주입한다. 인터페이스의 `Position` 프로퍼티는 저장된 사본을 반환하는 것이 아니라 접근 순간 `_rigidbody.position`을 읽으면 된다.

  ```csharp
  public interface IInteractionActor
  {
      Vector3 Position { get; }
  }

  public class Actor : MonoBehaviour, IInteractionActor
  {
      [SerializeField] private Rigidbody _rigidbody;

      public Vector3 Position => _rigidbody.position;
  }
  ```

  `InGameContent`에는 실제 `Actor` 참조를 직렬화하고 `builder.RegisterComponent(_actor).As<IInteractionActor>()` 형태로 등록한다. `InteractionUseCase`는 생성자에서 `Camera`와 `IInteractionActor`만 받으면 된다. 프로토타입 단계에서 추상화가 과하다고 판단하면 `Actor`를 직접 등록·주입해도 동작상 문제는 없지만, UseCase가 이동 명령까지 호출할 이유가 없다면 위치 전용 인터페이스가 의도를 더 정확하게 표현한다.

  플레이어가 런타임에 교체되거나 리스폰할 때 Actor 인스턴스 자체가 바뀌는 게임이라면 `IPlayerLocator`가 현재 Actor 참조를 보관하도록 확장할 수 있다. 이때도 위치를 매 프레임 복사하지 않고 `Current.Position`을 요청 시 읽는다. 현재처럼 씬 수명 동안 Actor가 하나로 고정된다면 Locator나 전역 위치 저장소 없이 씬 LifetimeScope에서 Actor를 직접 등록하는 편이 단순하다.

## 여러 Actor와 위치 저장소

- **Actor가 여러 개라면 `ActorPositionStore`를 만들고 모든 Actor의 위치를 저장해도 되는가?**  
  구현은 가능하지만 상호작용 거리 판정만을 목적으로 모든 위치를 매 프레임 복사하는 저장소를 만드는 것은 권장하지 않는다. Actor가 여러 개라는 사실과 이번 상호작용의 주체가 누구인지 결정하는 문제는 별개다. 플레이어 입력에서 시작한 상호작용이라면 `IControlledActorProvider.Current`처럼 현재 조작 중인 Actor 참조를 제공하고, NPC 명령에서 시작한다면 호출자가 자신의 Actor 참조 또는 Actor ID를 UseCase에 전달해야 한다. UseCase는 그 한 Actor의 실제 현재 위치만 읽으면 된다.

  여러 Actor를 중앙에서 다뤄야 한다면 위치 값의 사본을 보관하는 `ActorPositionStore`보다 Actor 참조를 등록하는 `ActorRegistry`가 먼저다. 등록소는 `ActorId -> IActorPosition`을 보관하고 `Position` 요청 시 각 Actor의 Rigidbody에서 현재 값을 읽는다. 이렇게 하면 Actor의 생성·제거·리스폰을 추적하면서도 위치 원본은 Rigidbody 하나로 유지된다.

  ```csharp
  public interface IActorRegistry
  {
      bool TryGet(ActorId id, out IActorPosition actor);
  }

  public interface IActorPosition
  {
      Vector3 Position { get; }
  }
  ```

  `ActorPositionStore`에 실제 위치 스냅샷을 저장할 이유가 생기는 경우는 네트워크 동기화, 리플레이, 저장·불러오기, 특정 시점의 고정된 AI 판단, 대량 Actor를 위한 공간 인덱스처럼 위치 이력이거나 동일 시점 스냅샷이 필요한 때다. 단순히 현재 위치를 조회하려는 경우에는 매 프레임 갱신 순서와 누락, Rigidbody와 사본 사이의 불일치를 추가할 뿐이다.

  상호작용 API도 주체가 명시되게 설계할 수 있다. 예를 들어 `TryInteract(ActorId actorId, RaycastHit hit)` 또는 `TryInteract(IActorPosition actor, RaycastHit hit)`처럼 호출자가 주체를 전달한다. 플레이어 전용 `InteractionUseCase`라면 `IControlledActorProvider`를 DI하고, 플레이어와 NPC가 공용으로 사용한다면 Actor를 메서드 인자로 전달하는 쪽이 자연스럽다.

## Actor 고유 ID와 내 Actor 관리

- **각 Actor가 고유 번호를 갖고, Store가 내 캐릭터 Actor와 모든 Actor를 구분해 보관하는 구조는 어떤가?**  
  이 경우 Store를 두는 방향은 타당하다. 다만 Store가 저장해야 하는 핵심은 매 프레임 복사한 위치가 아니라 `ActorId -> Actor 참조`의 등록 관계와 현재 내 캐릭터의 `ActorId`다. `MyActor`를 전체 목록과 별개의 또 다른 원본으로 중복 저장하기보다 `MyActorId`를 보관하고 전체 레지스트리에서 조회하는 파생 프로퍼티로 만들면 두 값이 서로 어긋나지 않는다.

  ```csharp
  public interface IActorStore
  {
      ActorId MyActorId { get; }
      IActor MyActor { get; }
      bool TryGet(ActorId id, out IActor actor);
      IReadOnlyCollection<IActor> All { get; }
  }
  ```

  개념적인 내부 상태는 `Dictionary<ActorId, IActor> actors`와 `ActorId myActorId` 두 가지면 충분하다. `MyActor`는 `actors[myActorId]`를 반환하고, 위치는 `MyActor.Position`을 호출하는 순간 실제 Rigidbody에서 읽는다. 이렇게 하면 Store는 Actor의 존재·식별·소유 관계를 관리하고 Actor는 자신의 실제 상태를 관리한다.

  규모가 커지면 전체 Actor 관리와 현재 조작 Actor 선택을 `ActorRegistry`와 `ControlledActorContext`로 분리할 수 있다. 전자는 등록·해제·ID 검색을 담당하고 후자는 `CurrentActorId`만 담당한다. 현재 규모에서는 하나의 `ActorStore`로 시작해도 되지만 공개 API에서 이 두 책임이 구분되어 있으면 나중에 분리하기 쉽다.

  `ActorId`의 생성 정책도 용도에 따라 달라진다. 한 번의 실행 동안만 식별하면 Spawn 시스템에서 증가하는 정수 ID로 충분하다. 저장·불러오기나 네트워크를 넘어 같은 Actor를 다시 찾아야 한다면 재사용되지 않는 안정적인 ID가 필요하다. 씬·프리팹에 단순히 정수 ID를 직접 입력하면 프리팹 복제로 중복되기 쉬우므로, 런타임 Actor는 Spawn/Registry가 ID를 할당하고 씬 고정 Actor는 에디터에서 생성한 고유 직렬화 ID를 검증하는 식으로 구분한다.

  `InteractionUseCase`는 플레이어 입력 전용이라면 `actorStore.MyActor`를 사용하면 된다. 모든 Actor가 사용할 공용 UseCase라면 `ActorId interactorId`를 메서드 인자로 받고 `actorStore.TryGet(interactorId, out actor)`로 주체를 찾는 편이 적절하다. 이 Store는 Actor 조회 저장소이므로 이름도 `ActorPositionStore`보다 `ActorStore` 또는 `ActorRegistry`가 책임을 더 정확하게 나타낸다.

## Actor 위치값 갱신 시점

- **`ActorStore`를 사용할 때 Actor의 위치값은 어떻게 갱신하는가?**  
  Store가 Actor 참조를 보관하는 구조라면 위치 갱신 메서드는 필요하지 않다. `Actor.Position`을 계산 프로퍼티로 만들고 조회 순간 실제 Rigidbody 위치를 반환한다. `actorStore.MyActor.Position` 또는 `actorStore.TryGet(id, out actor)` 뒤 `actor.Position`을 호출할 때 항상 현재 물리 상태를 읽으므로, Store와 Rigidbody 사이의 동기화 순서가 생기지 않는다.

  ```csharp
  public Vector3 Position => _rigidbody.position;
  ```

  Rigidbody로 움직이는 현재 Actor의 게임 규칙 판정에는 `_rigidbody.position`을 기준으로 사용한다. `transform.position`은 Rigidbody 보간이 활성화된 경우 렌더링용으로 보간된 위치일 수 있어 화면에는 부드럽지만 물리 시뮬레이션 위치와 미세하게 다를 수 있다. 상호작용 사거리, 충돌과 같은 게임 판정은 Rigidbody 위치가 일관되고, 카메라·UI 표시처럼 화면상 위치가 중요하면 Transform 위치가 적절할 수 있다.

  `AddForce`는 `FixedUpdate`에서 힘을 예약하고 그 뒤 물리 시뮬레이션에서 위치가 갱신된다. 이후 일반 `Update`에서 발생한 입력 처리 중 `Rigidbody.position`을 읽으면 마지막으로 완료된 물리 스텝의 위치를 얻는다. 따라서 상호작용 입력 시점에 별도 위치 복사 없이 바로 읽으면 된다.

  위치 스냅샷이 반드시 필요한 네트워크·리플레이·대량 공간 인덱스에서는 예외적으로 한 시스템이 정해진 틱에 모든 위치를 수집해야 한다. 그 경우 `UpdatePosition`을 각 Actor와 여러 시스템에서 제각각 호출하지 말고, 물리 스텝 이후의 한 시점에 Registry를 순회하여 `ActorId -> PositionSnapshot`을 원자적으로 갱신한다. 하지만 현재 상호작용 거리 검사에는 이 복잡성이 필요하지 않다.

## Actor 생성과 Store 등록 수명주기

- **Actor를 만들 때마다 Store에도 등록해야 하는가?**  
  Store가 현재 존재하는 Actor의 레지스트리라면 맞다. 생성 성공 직후 `Register`, 영구 제거 직전 또는 직후 `Unregister`가 반드시 한 쌍으로 실행되어야 한다. 그래야 ID 검색, 내 Actor 선택, 전체 Actor 순회가 실제 월드 상태와 일치한다.

  등록 책임은 각 Actor가 전역 Store를 찾아 스스로 등록하는 방식보다 Actor를 생성하는 `ActorSpawner` 또는 `ActorFactory`에 두는 것이 좋다. Factory는 ID 발급, Instantiate, 초기화, Store 등록을 하나의 흐름으로 처리하고, Despawn도 Store 해제와 GameObject 제거를 함께 처리한다. 등록 누락과 중복 ID를 한곳에서 검증할 수 있기 때문이다.

  ```csharp
  public IActor Spawn(ActorDefinition definition)
  {
      ActorId id = _idGenerator.Next();
      Actor actor = Object.Instantiate(definition.Prefab);
      actor.Initialize(id);
      _actorStore.Register(actor);
      return actor;
  }

  public void Despawn(IActor actor)
  {
      _actorStore.Unregister(actor.Id);
      Object.Destroy(actor.GameObject);
  }
  ```

  씬에 처음부터 배치된 Actor는 Instantiate를 거치지 않으므로 씬 Composition Root/LifetimeScope가 직렬화된 초기 Actor 목록을 등록하거나 별도의 `SceneActorRegistrar`가 시작 시 등록한다. 매번 `FindObjectsByType`으로 전역 탐색하기보다 명시적인 목록이나 스폰 경로를 사용하는 편이 누락 여부를 확인하기 쉽다.

  `OnEnable`에서 등록하고 `OnDisable`에서 해제하는 자동 방식도 가능하지만, 오브젝트 풀에서 잠시 비활성화하는 것이 월드에서 제거된다는 뜻인지 정책을 먼저 정해야 한다. 비활성 Actor도 Registry에 남아야 한다면 OnDisable 해제는 잘못된 동작이다. 따라서 등록·해제의 의미를 Spawn/Despawn 수명주기에 연결하는 편이 일반적으로 더 명확하다.

## UnitGenerator를 이용한 ActorId

- **Unity에서 `public readonly record struct ActorId(int Value);`를 쓸 수 없을 때 UnitGenerator로 처리할 수 있는가?**  
  가능하다. 현재 Unity 프로젝트의 컴파일 언어 버전은 C# 9이고 `record struct`는 C# 10 문법이므로 해당 선언을 사용할 수 없다. Cysharp UnitGenerator는 Unity 2022.3.12f1 이상을 공식 지원하며, C# 9에서도 사용할 수 있는 `[UnitOf(typeof(int))] public readonly partial struct ActorId { }` 선언으로 생성자, 값 비교, 해시 코드, `==`/`!=`, 명시적 변환, `AsPrimitive()` 등을 생성한다. 따라서 `Dictionary<ActorId, IActor>`의 키와 런타임 ID에 적합하다.

  ```csharp
  using UnitGenerator;

  [UnitOf(typeof(int))]
  public readonly partial struct ActorId
  {
  }
  ```

  Unity에서는 C# 11/.NET 7용 `[UnitOf<int>]`보다 `typeof(int)` 형식을 사용한다. 2026-08-21 AI 코드 작업에서 NuGetForUnity를 통해 UnitGenerator 2.0.0을 설치했다.

- **`[UnitOf(typeof(int))] public readonly partial struct ActorId`에서 에러가 나는 이유는 무엇인가?**  
  오류 발생 당시 프로젝트에는 NuGetForUnity만 있고 UnitGenerator 패키지는 설치되어 있지 않았다. NuGetForUnity는 NuGet 패키지를 설치하는 도구일 뿐 UnitGenerator를 함께 제공하지 않는다. 따라서 이 상태에서 선언을 사용하면 일반적으로 `UnitOf` 또는 `UnitGenerator` 네임스페이스를 찾을 수 없다는 컴파일 오류가 발생한다.

  먼저 NuGetForUnity를 통해 `UnitGenerator`를 설치하고 파일 위에 `using UnitGenerator;`를 추가해야 한다. 또한 현재 `ActorId.cs`에는 기존 `public class ActorId`가 남아 있으므로 그것과 새 struct를 동시에 선언하지 말고 기존 선언을 아래 코드로 교체해야 한다.

  ```csharp
  using UnitGenerator;

  namespace DataType
  {
      [UnitOf(typeof(int))]
      public readonly partial struct ActorId
      {
      }
  }
  ```

  채팅의 줄바꿈을 표시하던 `\` 문자를 실제 C# 파일에 붙여 넣었다면 모두 제거한다. 패키지를 설치했는데도 IDE에만 오류가 남으면 Unity가 패키지의 Source Generator를 다시 로드하도록 에디터 재시작 또는 Reimport를 시도한다. Unity Console에도 오류가 지속된다면 그때는 첫 번째 오류 메시지와 오류 코드를 기준으로 분석한다.

  2026-08-21 설치 결과는 `Assets/packages.config`의 `UnitGenerator` 2.0.0 항목, `Assets/Packages/UnitGenerator.2.0.0` 패키지 폴더, 생성기 DLL 메타 파일의 `RoslynAnalyzer` 라벨로 확인했다. `ActorId.cs`도 위의 강타입 struct 선언으로 교체했다. 동일 생성기 DLL과 C# 9를 사용한 독립 컴파일 검증에서는 `ActorId` 생성 코드, `AsPrimitive()`, 비교 연산자가 생성됐고 경고와 오류 없이 빌드됐다. 다만 프로젝트가 다른 Unity 인스턴스에서 열려 있어 Unity 배치 모드 검증은 프로젝트 잠금으로 실행할 수 없었으므로, 열린 에디터에서 에셋 새로고침 후 Console의 전체 프로젝트 컴파일 결과도 확인한다.

  UnitGenerator가 생성하는 내부 값은 `readonly` 필드이며, Unity 기본 직렬화는 readonly 필드를 직렬화하지 않는다. 따라서 UnitGenerator는 강타입 ID 생성 문제는 해결하지만 Unity Inspector/씬/프리팹 직렬화 문제까지 해결하지는 않는다. Spawn 시 런타임 ID를 할당한다면 직렬화가 필요 없으므로 그대로 사용한다.

  ```csharp
  private ActorId _id;
  public ActorId Id => _id;

  public void Initialize(ActorId id)
  {
      _id = id;
  }
  ```

  씬 고정 Actor의 ID를 Inspector에 저장해야 한다면 직렬화용 원시값과 런타임 강타입 ID를 분리한다.

  ```csharp
  [SerializeField] private int _serializedId;
  public ActorId Id => new ActorId(_serializedId);
  ```

  저장 데이터에서도 Unity `JsonUtility`를 사용한다면 원시 `int`를 저장하고 로드 후 `ActorId`로 변환하는 편이 단순하다. UnitGenerator가 공식 지원하는 직렬화 옵션은 System.Text.Json과 MessagePack 등이며 Unity 기본 직렬화는 별도 지원 대상이 아니다.
