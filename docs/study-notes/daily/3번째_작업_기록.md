# 3번째 작업 기록

- 작업 인덱스: 3번째
- 현재 단계: Farm 상호작용 상태 분리 → Progress 완료와 당근 생산 연결
- 대상 프로젝트: `UmamusumeTracenFarm`
- Unity 버전: 6000.5.7f1
- 작업 유형: 학습 중심 설계와 사용자 구현 검토

## 목표

FarmStore와 런타임 FarmProp을 이용해 현재 밭 상태를 조회·변경할 기반을 만든다. 밭에 한정되어 있던 작업자 수와 작업 진행도를 공통 Prop 상태로 분리하고, Progress가 완료되면 FarmModel의 완성 당근 수를 증가시킨 뒤 FarmProp의 당근 표현까지 갱신하는 단방향 흐름을 설계한다.

## 결과 요약

- Farm 전용 Payload를 공통 `IPropState`와 `PropState`로 일반화했다.
- `PropEntry`가 논리 상태와 실제 `IProp` 런타임 참조를 한 항목으로 묶도록 했다.
- `FarmStore`가 PropId를 기준으로 Entry를 등록하고 조회하도록 구성했다.
- `WorkingProgress`를 `ReactiveProperty<float>`로 변경했다.
- FarmProp이 Progress를 구독해 `Image.fillAmount`를 갱신하는 흐름을 구현하고 동작을 확인했다.
- 공통 `PropsProgressService`가 Store의 활성 Entry를 순회해 작업자 수에 비례하여 진행도를 계산하도록 했다.
- Progress 완료 상태를 나타내기 위해 `PropWorkingType`과 Complete 상태를 연결했다.
- AI가 특정 밭을 선택할 때 Payload와 런타임 Prop을 함께 조회할 구조를 검토했다.
- 완성된 당근 수는 FarmModel이 단일 원본으로 소유해야 한다는 규칙을 확정했다.
- Progress 완료 전달에는 VitalRouter를 사용하기로 결정하고 `PropWorkCompletedCommand` 타입을 준비했다.
- 현재 C# 프로젝트 빌드는 오류 0개로 통과했다.

## 주요 작업

### 1. FarmPayload와 FarmProp 책임 분리

초기 구조에서는 FarmProp이 작업 Progress, 작업자 수, 프로그레스바와 당근 활성화를 모두 직접 처리했다. 이 상태에서는 플레이어와 AI가 같은 밭에서 작업할 때 현재 상태를 공유하기 어렵고, 씬 밖의 시스템이 밭 상태를 조회할 수도 없다.

논리 상태와 Unity 표현을 다음과 같이 구분했다.

```text
PropState
├─ Id
├─ WorkingCount
├─ WorkingProgress
└─ WorkingType

FarmProp
├─ Transform과 Collider
├─ 프로그레스 Image
├─ 당근 GameObject 풀
└─ PropState를 화면에 표현
```

현재 상태 필드가 Farm 고유 정보가 아니라 작업 가능한 소품의 공통 정보이므로 `FarmPayload`보다 `PropState`라는 이름이 책임을 더 잘 나타낸다고 판단했다.

### 2. PropEntry와 FarmStore 연결

`PropEntry`는 `IPropState Payload`와 `IProp Prop`을 함께 보관한다. FarmStore는 Id를 키로 Entry를 등록하며 등록 시 Prop에 State를 초기화한다.

```text
InGameFlow.CreateMap()
→ PropState 생성
→ FarmStore.Register(state, prop)
→ PropEntry 생성
→ prop.Initialize(state)
```

이 구조로 AI와 UseCase는 Id를 통해 논리 상태와 현재 씬의 실제 Prop을 함께 찾을 수 있다. Store가 GameObject의 생명주기를 소유하는 것은 아니며, 현재 씬에 존재하는 Prop 참조를 등록해 제공하는 역할이다.

### 3. ReactiveProperty 기반 Progress 표시

`PropState.WorkingProgress`를 `ReactiveProperty<float>`로 만들었다. FarmProp은 초기화할 때 이를 구독하고 변경된 값을 프로그레스바에 반영한다.

```text
PropsProgressService
→ PropState.WorkingProgress.Value 변경
→ ReactiveProperty 알림
→ FarmProp.FillProgress(progress)
→ Image.fillAmount 갱신
```

Progress 값의 원본과 UI 표시값이 분리되었기 때문에 FarmProp의 Image는 더 이상 진행 상태의 저장 장소가 아니다. FarmProp 파괴 시 구독을 Dispose하는 수명 처리도 추가했다.

### 4. PropsProgressService 도입

여러 Prop의 진행도를 공통으로 갱신하기 위해 `PropsProgressService`를 추가했다. 이 서비스는 FarmStore의 Entry를 순회하고 작업자 수와 `Time.deltaTime`을 이용해 Progress를 계산한다.

```text
WorkingCount == 0
→ Progress 초기화
→ WorkingType.None

WorkingCount > 0
→ Progress 증가
→ 1에 도달하면 WorkingType.Complete
```

시간에 따른 갱신은 InteractionUseCase가 아니라 별도 ProgressService가 담당한다. UseCase는 작업 참여와 중단을 전달하고, ProgressService는 활성 작업의 시간 흐름을 계산한다.

### 5. Player와 AI가 같은 상태를 사용하는 구조

특정 Farm에 접근해야 하는 AI는 Payload만으로는 실제 위치와 상호작용 범위를 알 수 없다. 현재 PropEntry가 State와 IProp을 함께 제공하므로 AI는 작업 가능한 상태를 확인한 후 같은 Entry의 Prop을 이용해 위치 또는 상호작용 가능 여부를 판단할 수 있다.

장기적으로 이동용 정보가 필요하면 `IProp`에 접근 위치를 추가하거나 `IApproachable` 같은 인터페이스를 분리한다. 고정 도착점 하나로 충분하지 않은 큰 밭에서는 Actor 위치를 받아 가장 가까운 작업 지점을 반환하는 방식이 적합하다.

### 6. 완성 당근 수의 원본 결정

완성되었거나 수확 가능한 당근 수는 씬을 벗어나도 유지되어야 하므로 FarmModel이 원본으로 소유한다. 현재 `FarmModel.Value`가 이 역할을 하지만 의미가 불분명하므로 이후 `ReadyCarrotCount` 같은 이름으로 변경할 예정이다.

```text
Progress 완료
→ FarmService.GrowFarm(FarmId)
→ FarmModel의 완성 당근 수 +1
→ Repository 변경 알림
→ 화면용 Reactive Projection 또는 Presenter
→ FarmProp 당근 표시 갱신
```

FarmProp은 시작 시 슬롯 수만큼 당근을 미리 생성해 비활성화한다. 따라서 생산 완료마다 새로 Instantiate하지 않고 Model의 당근 개수만큼 기존 오브젝트를 활성화한다.

```csharp
for (int i = 0; i < _carrots.Count; i++)
{
    _carrots[i].SetActive(i < readyCarrotCount);
}
```

이 렌더 방식은 성장 완료, 저장 데이터 로드, 씬 재진입과 수확 후 감소에 모두 사용할 수 있다.

### 7. VitalRouter 완료 메시지 설계

공통 PropsProgressService가 FarmService를 직접 참조하지 않도록 Progress 완료를 VitalRouter Command로 전달하기로 결정했다.

```text
PropsProgressService
→ PropWorkCompletedCommand(PropType, PropId)
→ FarmService Route
→ GrowFarm(PropId)
→ FarmModel 갱신
```

프로젝트에는 VitalRouter 2.8.0이 설치되어 있고 `PropWorkCompletedCommand` 타입도 준비되어 있다. 다음 구현에서는 PropsProgressService에 `ICommandPublisher`를 주입하고 FarmService를 `[Routes] partial` Handler로 만든 뒤 RootLifeTimeScope에서 `routing.Map<FarmService>()`로 연결한다.

현재 VitalRouter 패키지와 Command 정의는 존재하지만 Publisher 발행, FarmService Route, Root Router 등록은 아직 구현되지 않았다.

## 현재 확인된 미완성 및 위험 요소

### 1. FarmProp의 기존 Progress 루프 중복

FarmProp에는 과거 구현인 `FillProgressAsync()`와 `_testIndex` 기반 당근 활성화가 남아 있다. 새 PropsProgressService와 동시에 실행되면 Progress 원본과 당근 개수가 다시 두 군데가 되므로 제거해야 한다.

### 2. 당근 Model과 View 연결 미완성

FarmService는 FarmModel 값을 변경할 수 있지만 Repository 변경 결과를 FarmProp의 당근 활성 개수로 전달하는 Presenter 또는 Synchronizer가 아직 없다.

### 3. VitalRouter 연결 미완성

`PropWorkCompletedCommand`는 정의되어 있지만 아직 발행·구독되지 않는다. 현재 Progress가 Complete가 되어도 FarmService.GrowFarm은 호출되지 않는다.

### 4. Progress 중단 규칙 확정 필요

현재 WorkingCount가 0이 되면 Progress가 즉시 0으로 초기화된다. 상호작용을 중단했을 때 진행도를 유지할지 초기화할지는 게임 규칙으로 확정해야 한다.

### 5. Store 이름과 범위

State와 Entry는 Prop 공통 구조로 일반화됐지만 Store 이름은 아직 FarmStore다. 향후 모든 Prop을 같은 Store에서 관리한다면 PropStore로 변경하고, Farm만 관리한다면 Farm 전용 Entry 또는 상태를 분명히 해야 한다.

## 최종 상태

오늘 작업으로 상호작용 Progress의 원본을 FarmProp UI에서 공통 PropState로 옮기고, ReactiveProperty를 이용해 화면을 갱신하는 데 성공했다. Progress 계산도 공통 PropsProgressService로 분리되어 플레이어와 AI가 같은 상태를 사용할 기반이 생겼다. 다음 핵심은 Complete 상태를 VitalRouter로 FarmService에 전달하고, FarmModel의 완성 당근 수가 변경되면 FarmProp의 미리 생성된 당근 표시가 같은 개수로 갱신되도록 연결하는 것이다.
